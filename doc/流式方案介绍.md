# 流式方案介绍

本文档描述本地音乐播放器的**流式解码播放方案**，并与当前“按需全量解码到内存”的方案进行对比，给出优劣势分析与最小可行架构设计（MVP）。

## 方案对比：流式 vs 当前方案

**当前方案（按需全量解码到内存）**
- 切歌时将整首解码（必要时重采样）到 `AudioBuffer`，播放线程直接读内存。

**流式方案（边解码边播放）**
- 解码线程持续产出 PCM 写入 ring buffer，音频回调线程只读 ring buffer。

### 优势（流式方案）
- **内存占用稳定**：ring buffer 固定容量（几十 KB 到数 MB），峰值内存可控。
- **首播延迟更低**：只需缓冲少量 PCM 即可开始播放。
- **适配长音频**：长时音频、无损高码率不会导致内存暴涨。
- **更适合低配设备**：内存压力小，整体系统稳定性更高。

### 劣势（流式方案）
- **实现复杂度高**：多线程 + ring buffer 同步，bug 风险更高。
- **欠流风险**：解码速度不足时会出现静音/卡顿，需要补偿策略。
- **Seek 更复杂**：需要重置解码器、清空 buffer、重新解码。
- **测试成本高**：需要覆盖多格式、多设备、多线程场景。

### 优势（当前方案）
- **实现简单、维护成本低**：逻辑清晰，定位问题容易。
- **播放期间稳定**：只要内存够，播放不会欠流。
- **Seek 速度快**：PCM 全量在内存，直接跳 offset。

### 劣势（当前方案）
- **内存压力大**：随音频长度和格式线性增长。
- **首播延迟明显**：切歌需要完整解码。
- **不适合长音频/高码率**：容易出现内存峰值过高。

### 商业化建议
- **短期交付 / MVP**：当前方案更稳、更快、更省开发成本。
- **中长期扩展**：流式方案更可扩展，适合无损、高码率与长音频场景。

## 流式方案最小可行架构（MVP）

### 1. AudioRingBuffer
- 线程安全的循环缓冲区。
- 提供 `write(const void*, size)` / `read(void*, size)` / `size()` / `capacity()`。
- 固定容量，例如 1–4MB（可配置）。

### 2. AudioStreamDecoder
- 独立解码线程。
- 持有 `ExtractorHelper` + `AudioDecode` / `FLACDecode` / `VorbisDecode`。
- 解码后写入 `AudioRingBuffer`。
- 支持：`start(path)` / `stop()` / `seek(ms)` / `flush()`。

### 3. MusicPlayer 接入
- `getAudioData()` 只读 ring buffer。
- buffer 不足则填静音，避免崩溃或爆音。
- 切歌时：停止旧 decoder → 清空 ring buffer → 启动新 decoder。

### 4. MusicPlayList 变化
- 只维护 `Extractor` + `AudioSpec` + 元信息。
- 不再创建全量 `AudioBuffer`。

---

## 数据流（简化）

1. `MusicPlayer::play()` → `AudioStreamDecoder::start(path)`
2. 解码线程循环解码 → 写入 ring buffer
3. `AudioDevice` 回调 `getAudioData()` → 从 ring buffer 取 PCM
4. ring buffer 不足 → 填静音
5. `seek()` → 重置解码器 + 清空 buffer + 从新位置继续解码

---

## 实施建议（阶段性）

1. 先实现 ring buffer + 音频回调读写（无解码）
2. 接入一种主流格式（如 MP3/AAC）验证稳定性
3. 扩展到 FLAC/Vorbis 等特殊格式
4. 最后加入 seek 与预读优化

## 预估成本

- 开发改动：约 400–800 行代码
- 开发时间：1.5–3 天（熟悉项目情况下）
- 测试时间：1–2 天（多格式、多设备场景）
