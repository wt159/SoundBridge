# SoundBridge 代码开发方向建议

本文结合当前仓库结构（`sdk/extractor`、`sdk/audio`、`sdk/test`、`sdk/log`）给出若干可落地的开发方向，适合作为未来 1~3 个迭代周期的规划输入。

## 方向一：提取器（Extractor）插件化与自动注册

### 现状观察
- 目前 `ExtractorFactory` 通过 `switch + enum` 创建提取器，新增格式时需要同时改动 map/enum/factory 分支，耦合度较高。
- 已支持多种格式（WAV/AAC/MP3/FLAC/M4A/OGG/AIFF/ASF），说明这是系统核心能力，后续继续扩展的概率高。

### 建议目标
- 把“格式识别 + 对应提取器构造”改成注册表机制：每个提取器在编译期或初始化阶段自注册。
- 将文件扩展名匹配升级为“扩展名 + 头部魔数探测”双路策略，降低误判。

### 分阶段落地
1. 增加 `IExtractorCreator` 抽象和注册中心（`std::unordered_map<std::string, Creator>`）。
2. 给现有提取器增加注册宏（例如 `REGISTER_EXTRACTOR(".mp3", MP3Extractor)`）。
3. 为每个提取器补充 `sniff()` 接口，支持按文件头探测。
4. 为工厂补齐单测：扩展名命中、魔数命中、冲突优先级、未知格式回退。

### 收益
- 新增格式成本从“多点改动”降为“新增一个提取器文件 + 注册”。
- 降低工厂复杂度，改善可测试性。

---

## 方向二：播放链路异步化与缓冲策略优化

### 现状观察
- 播放列表和解码处理里已经有 `WorkQueue`、`AudioDecodeProcess`、`AudioResample` 等组件，具备流水线基础。
- `MusicPlayList` 里含多处原子变量与跨组件状态，说明并发路径较重，容易出现抖动、切歌卡顿、状态竞争。

### 建议目标
- 建立明确的三段流水线：读取/提取 -> 解码 -> 重采样/输出。
- 引入“预缓冲阈值 + 回填策略 + 丢包保护”机制，优先保证稳定播放。

### 分阶段落地
1. 为每段流水线定义统一数据包结构（含时间戳、帧号、格式信息）。
2. 在播放前增加预加载阈值（如 > 200ms PCM 数据才启动设备）。
3. 引入高低水位线：低于低水位触发加速生产，高于高水位暂停上游任务。
4. 增加切歌策略：旧任务软取消 + 新任务优先执行，避免队列长尾。

### 收益
- 降低短时 I/O 波动导致的爆音/静音。
- 切歌与快进场景下用户体验明显提升。

---

## 方向三：统一错误码体系与可观测性（日志/指标）

### 现状观察
- 代码中已使用 `LogWrapper`，但错误传播大多依赖返回值，缺少统一错误语义。
- 测试文件较多，适合引入“可观测性驱动调试”的工程习惯。

### 建议目标
- 构建统一错误码：模块、严重级别、可恢复性、建议动作。
- 在关键路径打点：打开文件耗时、首帧时间、平均解码耗时、重采样耗时、缓冲命中率。

### 分阶段落地
1. 新建 `ErrorCode.hpp`（比如 `SB_ERR_EXTRACTOR_UNSUPPORTED`、`SB_ERR_DECODE_CORRUPTED_FRAME`）。
2. 替换关键模块裸 `int` 返回，改为 `Result<T, ErrorCode>` 或最小化包装体。
3. 在日志中统一输出 traceId（每次播放会话一个 ID）。
4. 补充简单 metrics 导出接口（控制台/文件均可）。

### 收益
- 线上问题定位从“猜测”变为“数据驱动”。
- 降低跨模块协作时的沟通成本。

---

## 方向四：测试体系升级（样本库 + 回归基线）

### 现状观察
- 现有 `sdk/test` 以可执行测试程序为主，便于调试，但自动化回归能力有限。
- 仓库中已有不同格式的音频样本，可进一步沉淀为规范样本库。

### 建议目标
- 将“能跑通”升级为“可回归、可比较、可量化”。
- 建立音频解码/重采样输出的基线校验（时长、采样率、声道、哈希/波形统计）。

### 分阶段落地
1. 规范测试资产目录：按编码格式、采样率、声道数分桶。
2. 为关键测试增加断言输出（JSON 报告），便于 CI 解析。
3. 增加故障样本（截断帧、错误头、超大标签）做鲁棒性测试。
4. 在 CI 中配置最小回归集（短样本）与夜间全量集（长样本）。

### 收益
- 防止“修 A 破 B”的回归风险。
- 对性能和质量有持续可见的数据闭环。

---

## 方向五：跨平台输出设备抽象与延迟优化

### 现状观察
- 工程已包含音频设备相关测试，说明输出层是核心能力之一。
- 若要面向桌面/嵌入式扩展，设备层接口和时钟同步能力会成为瓶颈。

### 建议目标
- 抽象统一 `IAudioSink` 接口，屏蔽底层设备差异。
- 引入端到端延迟监控与动态补偿（重采样微调、缓冲策略自适应）。

### 分阶段落地
1. 提炼设备能力矩阵（支持格式、最小缓冲、回调模型）。
2. 增加延迟测量点：提交时间、设备回调时间、实际播放估算时间。
3. 在长时播放中实现 drift 检测（播放时钟与源时钟偏差）。
4. 使用微幅 resample 比率修正偏差，减少累计卡顿。

### 收益
- 多平台接入成本下降。
- 在低性能设备上也能保持稳定听感。

---

## 方向六：API 设计与二次封装（面向上层业务）

### 现状观察
- 当前播放器能力已具备列表、切歌、播放控制等基础接口。
- 若未来要被 App/UI 层复用，需要更稳定、可文档化的公共 API。

### 建议目标
- 形成分层 API：底层流处理 API + 高层播放器 API。
- 补全事件模型（状态机）与线程安全约定，降低业务误用概率。

### 分阶段落地
1. 定义播放器状态机（Idle/Preparing/Playing/Paused/Stopped/Error）。
2. 统一事件回调语义（线程上下文、顺序保证、重入约束）。
3. 输出 API 文档（参数、返回值、错误码、时序图）。
4. 提供一个轻量示例（CLI 或简单 UI）作为 SDK 接入模板。

### 收益
- 提升 SDK 可复用性与可维护性。
- 缩短上层业务开发周期，减少接入 bug。

---

## 推荐优先级（务实版本）

如果希望在有限资源下快速见效，建议优先顺序：
1. **测试体系升级（方向四）**：先建立质量护栏。
2. **错误码与可观测性（方向三）**：提升定位效率。
3. **播放链路缓冲优化（方向二）**：直接改善体验。
4. **提取器插件化（方向一）**：为格式扩展做长期准备。
5. **设备层抽象（方向五）**：按平台需求推进。
6. **API 封装（方向六）**：在对外复用需求明确后推进。
