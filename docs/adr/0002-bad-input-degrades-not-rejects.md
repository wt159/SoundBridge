# 0002 坏数据只降级，不按格式分叉

- 状态：已接受
- 日期：2026-11-03
- 来源：[#27](https://github.com/wt159/SoundBridge/issues/27)、[#28](https://github.com/wt159/SoundBridge/issues/28)、[#29](https://github.com/wt159/SoundBridge/issues/29)

## 背景

地图 #22 的十张票把所有受支持格式都实测了一遍，发现同一个坏法在不同格式上给出**相反**的处置：

- 丢掉文件最后 128 字节（约 0.016%）：flac 播 99.75%，mp3 和 mkv 完好无损，而 wav、aiff、ogg、ape、m4a、asf **一个字都播不出来**；
- 流内零化 400 字节：wav/aiff/mkv 解出等长垃圾、无任何信号；flac 报了三次 `LOST_SYNC` 但只进日志；ogg init 成功却 0 字节无错；mp3/aac/ape/m4a/asf 一坏就整段停。

这些差异没有一条来自格式的语义差别，全部来自实现细节（是否检查短读、是否把已解部分丢掉、是否读错误回调）。

## 决策

**处置只看「解出多少帧」，不按格式分叉。**

- 解得出就播——能解多少播多少，不因为文件不完整就拒绝一个还能放的音频；
- 解不出才拒绝，且**拒绝的唯一出口是 `createExtractor() == nullptr`**；
- 同一坏法在不同格式上给出相反处置，记为**实现缺口**，不是规格例外。

已知唯一例外是 ogg 的截断：拒绝发生在第三方 demux 的页链校验里，自有代码没有 clamp 的着力点，所以写死「ogg 的截断一律拒绝」。

## 考虑过的替代方案

**按格式分别定义期望行为。** 这是现状的隐含做法，也是实测出来的十种行为。否决理由：用户不理解「为什么这个文件少了 100 字节还能放，那个少了 3 个采样就完全打不开」，而且每加一个格式就要重开一次讨论。

**加一层「坏文件修复」**（补齐尾部、重建索引）。否决理由：修不好。没有任何格式能凭空补出缺失的样本，假装修好只会让用户听到错误的内容还以为正常。

## 后果

- wav/aiff 的 `initCheck` 语义变了：clamp 之后会从「打不开」变成「能打开但短」，`durationMs` 与实测首次出现分歧。凡是用 `initCheck() != OK` 当「文件坏了」的地方（如 `RealMediaFixture::create`）都要顺带扫一遍调用点。
- 拒绝路径少了九处分支，多了一个出口，错误码的边界也变清楚了：按「扩展名是否注册」分，不按「哪个格式解析失败」分。
- 「坏帧」和「截断」的判别原则被固定下来：**坏帧之后还有数据，截断之后没有**。前者跳过继续，后者播到坏处为止。两者共用同一套时长判据（`±max(5%×good, 150ms)`），但期望值方向相反。
- 判据必须用播放路径量测（`AudioStreamDecoder` + ring），不能用离屏整段解码器——后者在解码失败时丢弃已解部分，会把「播到 90% 才报错」错记成「拒绝」。见 `doc/bad-input-spec.md` 第 0 节 B4。
